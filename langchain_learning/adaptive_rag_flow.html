Adaptive RAG + CRAG

How the coffee-guide example selects a retrieval strategy, checks whether its evidence is enough, and searches the web when the local knowledge base cannot answer.

End-to-end flow

The router chooses one retrieval method. CRAG then evaluates the returned passages before they reach answer generation.

Worked trace for your question

Your question: “How does the code determine that the proper document wasn’t found in Pinecone and that it should call the web?”

  1. Read configuration and prompt for the question.

    main() loads .env, checks that PINECONE_API_KEY exists, then reads the question. Since you provided one, it uses that text rather than the sample question.

  2. Prepare and upsert the local coffee knowledge base.

    The script loads the HTML files from coffee_pages, adds category metadata, splits them into chunks, embeds them, and upserts them to Pinecone under the adaptive-rag namespace using deterministic IDs. This happens on each run before retrieval.

  3. Choose Simple Similarity for this wording.

    choose_strategy() checks for a category plus a metadata cue to select Self-Query, then checks for configured broad/comparison phrases to select MultiQuery. Your question has neither, so the code falls through to SIMILARITY. This selection does not mean a document has or has not been found.

  4. Ask Pinecone for up to six candidate passages.

    The selected retriever runs .invoke(question). Similarity search returns its top matches; in this code there is no explicit similarity-score cutoff that says “not found.” Returned documents are deduplicated by source and text.

  5. Ask the CRAG grader if those passages can answer the question.

    correct_retrieval() first asks local Ollama to assess each passage individually and keeps passages marked relevant. It then asks whether those selected passages together are sufficient. This is a model judgment—not a Pinecone “not found” response or a numeric similarity threshold.

  6. Try alternate web providers only when local evidence is insufficient.

    If Pinecone returned no documents, grading is skipped and web search is called. If the grader finds no relevant passage or judges the selected passages insufficient, the web fallback is called. When it runs, the original question is sent to Yahoo, Brave, Startpage, then Mojeek, stopping at the first provider with usable results. If local evidence is sufficient, the code keeps it and skips web search.

  7. Rerank evidence and generate the answer.

    Web results with snippets become documents. The CrossEncoder ranks the chosen evidence and keeps up to three passages; then Ollama generates an answer using only those passages and cites their source. If web search yields no usable snippets, the program stops instead.

In short: Pinecone supplies candidates; the local Ollama grader checks individual passages, then the sufficiency of the selected evidence. An empty candidate list or insufficient local evidence triggers web search. There is no separate Pinecone score threshold in the current code.

Which route fits which question?

Simple similarity

Choose this for a direct question without a special routing cue. Pinecone returns semantically similar chunks.

“How is cold brew coffee made?”

MultiQuery

Choose this for broad or comparative questions. The local LLM creates alternate phrasings; retrieval includes the original question too.

“Compare different coffee brewing methods.”

Self-Query

Choose this when a known category is paired with a metadata cue. The LLM creates a semantic query and a Pinecone metadata filter.

“Find the cold brew guide.”

CRAG: what happens when evidence is missing?

  • Local evidence is sufficient: Keep local passages, skip web search, rerank with the CrossEncoder, and answer from the top three.
  • Local evidence is insufficient or empty: Search try Yahoo, Brave, Startpage, then Mojeek, turn results with snippets into evidence documents, rerank, and answer from the top results.
  • No usable web snippets: Stop rather than generate an answer without supporting context.

Notes about this learning example

The strategy router uses keyword rules, while the CRAG sufficiency check uses the local Ollama model. When the fallback runs, the question is sent to the first configured search provider that returns usable results. The embeddings use Ollama's nomic-embed-text model in the separate Pinecone index coffeeindex-ollama; the CrossEncoder reranker still downloads its model from Hugging Face if it is not cached. Pinecone is a hosted database, so upserting and retrieving vectors still require a network connection. Pull the embedding model with ollama pull nomic-embed-text before running. The runnable Python implementation is adaptive_rag_learning.py.
