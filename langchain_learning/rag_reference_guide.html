1. RAG: the big picture

Retrieval-Augmented Generation (RAG) combines a search system with a language model. Rather than asking the model to answer from its training memory alone, the application finds useful material in a knowledge base and places it in the model's context.

Question │ ▼ Find relevant document chunks ──► Assemble evidence/context │ ▼ LLM writes an answer │ ▼ Answer + sources

Retrieval

Finds candidate chunks related to the user's question.

Augmentation

Adds those chunks, and often their source metadata, to the prompt.

Generation

Uses the question and retrieved context to produce a natural-language answer.

A useful mental model is an open-book exam: retrieval finds the pages, and the model explains them. If retrieval misses the needed information, a fluent answer may still be wrong—so good retrieval and evidence checks matter.

2. Preparing and storing documents

The ingestion pipeline turns source files into searchable records. It is normally run when content is added or updated, not every time a user asks a question.

  1. Load: read HTML, PDF, text, or another source format.
  2. Clean: remove navigation, repeated boilerplate, and unusable markup.
  3. Split: divide long content into overlapping chunks.
  4. Enrich: attach useful metadata such as category, source, date, and access scope.
  5. Embed: turn each chunk into a numeric vector.
  6. Upsert: save vector, text, and metadata under an ID in the vector store.

What is stored?

{
  "id": "stable-id-for-this-chunk",
  "values": [0.12, -0.08, 0.44, "..."],
  "metadata": {
    "text": "Cold brew coffee is made by steeping...",
    "source": "cold_brew.html",
    "category": "cold_brew"
  }
}

The vector is used for nearest-neighbor search. The text is the readable evidence later sent to the LLM. Metadata supports filtering, source display, access checks, and document lifecycle management.

Chunking: too large vs. too small

Chunking issueWhat can happenPractical direction
Chunks too largeUseful details are surrounded by unrelated material; context can exceed prompt budget.Split along headings, paragraphs, or semantic boundaries; tune using a test set.
Chunks too smallDefinitions and their explanations may be separated; retrieved evidence loses context.Keep coherent ideas together and add modest overlap when boundaries risk losing meaning.
Overlap too highNearly identical chunks are stored and returned repeatedly.Deduplicate and choose overlap based on content structure, not by habit.

IDs and upserts

An upsert inserts a new vector or replaces the vector that already has the same ID in the same index and namespace. A stable ID can make ingestion repeatable. If identical content receives different IDs, both records may remain. Changing an embedding model requires re-embedding the corpus and using a compatible index dimension.

Metadata must be designed deliberately. In your example, filenames become categories such as cold_brew, espresso, and pour_over. A metadata filter only works if those fields and values were actually stored with the vectors.

3. Embeddings and vector search

An embedding model maps text to a fixed-length list of numbers. Texts that the model considers semantically related often have vectors that are near each other under a chosen distance or similarity metric.

"How do I make cold brew?" ──embed──► [0.18, -0.42, 0.07, ..., 0.31]

At query time, the question is embedded using a compatible model. The vector store compares that query vector with stored chunk vectors and returns nearest candidates.

Important compatibility rule

Use the same embedding model (and compatible settings) for documents and questions. The vectors need matching dimensions and a shared embedding space. A vector from one model generally cannot be compared meaningfully with a vector from another model, even if both have the same dimension.

Similarity search is candidate generation

A nearest chunk is not automatically a good answer. If the database only contains coffee-brewing pages, a restaurant question still gets the “nearest” brewing chunks. Search can return the least-distant options even when none truly answer the question. Use relevance checks, thresholds calibrated on data, or a fallback path to handle this.

A vector store usually returns a top k list. “Top results” means best among what is stored—not proof that any result is relevant.

4. Cosine similarity and Euclidean distance

Both metrics compare vectors, but they measure different geometric properties. Their usefulness depends on the embedding model, normalization, index configuration, and the task.

Cosine similarity: angle / direction

cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)

Cosine similarity measures how aligned two vectors are, largely ignoring their magnitudes. Its mathematical range is from -1 to 1; embedding distributions and systems may occupy a narrower range. Larger values mean more aligned directions.

Euclidean distance: straight-line distance

euclidean_distance(A, B) = sqrt( Σᵢ (Aᵢ - Bᵢ)² )

Euclidean distance measures straight-line separation. Smaller distance means closer vectors.

PropertyCosine similarityEuclidean distance (L2)
MeasuresDirection / angleAbsolute geometric distance
Better matchHigher scoreLower distance
Magnitude matters?Mostly noYes
Often useful whenSemantic direction is the intended signalVector magnitudes and geometry are meaningful

A tiny example

Let the query be A = (1, 0):

  • B = (1, 1) points partly in the same direction as A. Its cosine similarity is about 0.707.
  • C = (0, 1) is perpendicular to A. Its cosine similarity is 0.
  • Euclidean distances are distance(A, B) ≈ 1.0 and distance(A, C) ≈ 1.414.

For unit-normalized vectors, cosine and Euclidean distance induce the same ranking because ||A - B||² = 2(1 - cosine_similarity(A, B)). Without normalization, rankings can differ.

Don’t compare raw scores across different models, metrics, or APIs as if they had one universal meaning. A score of 0.7 is not automatically a 70% probability of relevance. Calibrate any cutoff on labeled examples.

5. How HNSW works

HNSW means Hierarchical Navigable Small World. It is an approximate nearest-neighbor indexing method used by some vector search systems. Approximate search trades a small chance of missing the exact nearest neighbor for faster lookup at scale.

Think of it as several linked maps of the same points:

Top layer: A ─────────────── G │ │ Middle layer: A ─── C ───────── G ─── J │ │ │ │ Base layer: A─B─C─D─E─F─G─H─I─J─K─L Search: enter at a sparse upper layer, move toward the query, descend to denser layers, then refine among nearby candidates.
  1. Start at an entry point in a sparse upper layer.
  2. Move greedily to linked points that are closer to the query.
  3. Descend to the next, denser layer and continue exploring.
  4. Search more candidates in the base layer and return the nearest found.

Common HNSW tuning concepts include M (graph connections), efConstruction (construction-time search breadth), and efSearch (query-time search breadth). More connections or broader search can improve recall but use more memory or latency.

HNSW explains one way to implement fast vector search. It does not mean every vector database, including a managed service, exposes or uses HNSW in exactly the same way. Treat Pinecone’s managed indexing internals as provider-specific unless its current documentation says otherwise.

6. Basic similarity retrieval

Basic retrieval embeds the question, searches for its nearest vectors, and returns the top k documents. It is a good starting point when the question is clear and the content is well represented in the index. 

question = "How do I make cold brew coffee?"
documents = vector_store.similarity_search(question, k=3)

In the coffee knowledge base, this question should retrieve the cold brew guide:

Evidence: “Cold brew coffee is made by steeping coarse coffee grounds in cool water for an extended time. After steeping, strain the grounds and serve the coffee over ice or dilute it to taste.”

Search and answer generation are separate steps. Retrieval returns Document objects; the application must still supply them to an answer model if a generated answer is needed.

7. MultiQuery retrieval

Users can express one information need in several ways. MultiQuery asks an LLM to produce alternate phrasings, retrieves for those phrasings, and typically includes the original query too. The returned document lists are combined; duplicates may need to be removed.

Original: "Compare ways to make coffee" │ ▼ LLM query expansion ├── "What are the differences between cold brew and espresso?" ├── "Which coffee brewing methods use hot water?" └── "How do manual and pressure-based coffee methods compare?" │ ▼ Search each query → combine candidate chunks → deduplicate

Use it when: the question is broad, ambiguous, comparative, or likely to have varied terminology.

Trade-offs: extra LLM and vector-search work adds latency and cost, and generated queries can drift away from what the user asked. Keep the original query in the search set and evaluate whether expansion improves recall.

8. Self-Query retrieval

Self-Query converts a natural-language question into two parts: a semantic search query and, when appropriate, structured metadata filters or constraints.

Question: "Show me only the espresso guide" │ ▼ LLM query constructor ├── Semantic query: "espresso brewing guide" └── Metadata filter: category == "espresso" │ ▼ Vector search + metadata filter → matching chunks

Use it when: users ask for things such as a category, source, date range, product, or other field that is represented in metadata.

Prerequisites: metadata must be present and consistently typed; the LLM must know the allowed fields and values; and the query translator must map the generated filter to the vector store's filter syntax.

Self-Query is not simply “search the text for a category word.” It is an LLM-assisted structured-query step. In the learning code, the route to Self-Query is separately chosen by simple keyword rules.

9. Reranking

Retrieval is often tuned to find a broad set of possible matches (high recall). A reranker then examines the question and each candidate together and reorders them by estimated relevance (higher precision).

Question + top 6 retrieved chunks │ ▼ Cross-Encoder scores each pair │ ▼ Keep best 3 chunks for answer

A bi-encoder embeds question and documents separately, which makes large-scale search efficient. A cross-encoder reads the question-document pair jointly, often giving a better relevance order at a higher per-candidate cost. Its score is a ranking signal, not necessarily a calibrated probability.

10. Adaptive RAG

Adaptive RAG selects a retrieval path based on the question, the available evidence, or system state. The goal is to spend effort where it helps: simple questions can use simple retrieval; broad questions can use query expansion; structured constraints can use metadata filters.

Question patternStrategyCoffee example
Direct, specific factSimple similarity“How is cold brew made?”
Broad or comparative; wording may miss relevant termsMultiQuery“Compare different coffee brewing methods.”
Explicit structured constraintSelf-Query“Find the espresso guide.”
Retrieved evidence does not answer the questionCRAG-style correction / web fallback“Which restaurant in Bangalore serves cold coffee?”
Adaptive RAG is an orchestration idea, not one particular model or retriever. The router can be rules-based, model-based, or learned from evaluated examples. A simple router is easier to understand, but it may miss paraphrases or choose the wrong path.

What your learning example currently does

  • Routes to Self-Query if a known category and a metadata cue are present.
  • Otherwise routes to MultiQuery if it sees configured comparison/breadth phrases.
  • Otherwise uses simple similarity search.
  • Then applies a local Ollama evidence check and a web-search fallback if local evidence is insufficient.

This is a transparent keyword-based teaching router, not yet a general intent classifier. The exact code is in adaptive_rag_learning.py.

11. Corrective RAG (CRAG)

CRAG adds a correction step after retrieval. It checks whether retrieved evidence is useful and sufficient; if not, the system can refine retrieval, search another source, or decline to answer.

Question → local retrieval → grade evidence │ ┌─────────────┴─────────────┐ │ │ Sufficient evidence Insufficient / empty │ │ Keep local evidence Search fallback source │ │ └─────────────┬─────────────┘ ▼ Rerank → grounded answer

In your example, Ollama grades Pinecone passages individually, keeps relevant ones, then judges whether the selected evidence is enough for the question. If not—or if no passages were returned—the code tries YahooBrave StartpageMojeek in sequence and stops at the first provider returning usable results.

The grader is an LLM and can be wrong. It may reject a useful short passage or accept weak evidence. Test it on representative questions. Also, the search fallback sends the user's query to an external provider.

The current fallback converts search-result snippets into documents; it does not fetch or independently verify every linked webpage. Source URLs should therefore be treated as references, not proof that the full page was checked.

13. What production readiness adds

A RAG system can demonstrate many techniques and still not be production ready. Production readiness means the whole service is reliable, secure, measurable, maintainable, and suitable for its intended users.

AreaQuestions to answer before production
IngestionHow are changes detected, versions tracked, stale vectors removed, and retries made safe?
Retrieval qualityDoes a test set measure recall, precision, filters, and retrieval failures?
Answer qualityAre claims supported by cited passages? What happens when evidence is weak?
SecurityAre secrets managed securely? Are tenant and document permissions enforced at retrieval time?
Prompt injectionAre retrieved documents treated as untrusted data and prevented from overriding system instructions?
OperationsAre there timeouts, retries, rate limits, concurrency controls, and clear dependency-failure behavior?
MonitoringAre latency, search quality, fallback rate, errors, model versions, and cost recorded without leaking sensitive text?
PrivacyWhich data can be sent to a hosted vector service or external web search?
Cost and scaleAre embedding, query expansion, reranking, and generation costs bounded and understood?

Practical next steps for this demo

  1. Move document loading and vector upserts into a separate ingestion command.
  2. Create a small, labeled evaluation set covering each route and “not in knowledge base” questions.
  3. Measure retrieval quality and grader false-accept / false-reject rates before tuning thresholds.
  4. Handle search-provider and model failures with explicit, user-friendly outcomes.
  5. Make source citations traceable to the exact chunks used in each answer.
  6. Decide whether user queries may be sent to external search providers.

14. Glossary and review questions

TermPlain-language meaning
DocumentA source item or a piece of it, often represented by text plus metadata.
ChunkA manageable segment of a larger document that can be embedded and retrieved.
EmbeddingA vector representation of text produced by an embedding model.
Vector storeA system that stores vectors and supports nearest-neighbor search and often metadata filters.
Top-kThe k highest-ranked candidates returned by a search.
Metadata filterA structured condition, such as category equals espresso, applied to records.
RecallHow many of the truly relevant items retrieval manages to find.
PrecisionHow many returned items are actually relevant.
RerankerA second-stage model that reorders retrieved candidates for a specific query.
GroundingConstraining an answer to evidence supplied in context and citing that evidence.
FallbackAn alternate path used when the preferred retrieval path cannot answer.
